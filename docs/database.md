# Database (MySQL 8)

Files:

* `database/schema.sql` creates all tables. It is idempotent and drops existing JobSense tables first.
* `database/seed.sql` holds the admin account, skill taxonomy, career paths, career skills and
  learning resources. It is generated by `backend/scripts/generate_seed.py`; do not edit it by hand.

All tables use InnoDB and `utf8mb4_unicode_ci`.

## Setup

```sql
CREATE DATABASE jobsense CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

```bash
mysql -u root -p jobsense < database/schema.sql
mysql -u root -p jobsense < database/seed.sql
```

Or, with `backend/.env` configured, run `flask --app run init-db` from `backend/`. This
creates the database if it is missing, then runs both files.

## Entity overview

```
users 1-1 user_profiles
users 1-* user_sessions, user_interests, resumes, candidate_skills,
          job_matches, saved_jobs, applications, career_recommendations
jobs  1-* job_matches, saved_jobs, applications
career_paths 1-* career_skills, career_recommendations
learning_resources   (keyed by canonical skill_name)
skill_taxonomy       (reference data mirrored from the extractor's taxonomy)
```

## Tables

| Table | Key columns | Notes |
|---|---|---|
| **users** | user_id PK, email UNIQUE, password_hash, role ENUM(candidate, admin), is_active, created_at, updated_at | password_hash is never returned by the API |
| user_sessions | session_id PK, user_id FK, token_hash CHAR(64) UNIQUE, expires_at | stores SHA-256 of the bearer token only |
| user_profiles | user_id PK/FK, headline, experience_years, experience_summary, education, location, preferred_locations, remote_preference | created with the user |
| user_interests | interest_id PK, user_id FK, interest; UNIQUE(user_id, interest) | career recommendation signal |
| skill_taxonomy | taxonomy_id PK, skill_name UNIQUE, category, aliases (JSON) | 137 skills |
| **resumes** | resume_id PK, user_id FK, file_name, file_type ENUM(pdf, docx), file_path (random server name), file_size, extracted_text, processed_text, education, experience (JSON), experience_years, status, error_message, is_active, uploaded_at, processed_at | one active resume per user; older uploads kept as history |
| **candidate_skills** | skill_id PK, user_id FK, skill_name, normalized_skill_name, source ENUM(resume, manual); UNIQUE(user_id, normalized_skill_name) | resume skills are replaced on re-upload; manual ones are kept |
| **jobs** | job_id PK, external_job_id, title, company, location, country, description, processed_text, job_url, job_url_hash, employment_type, remote, required_skills (JSON), min_experience_years, source, publisher, posted_at, fetched_at; UNIQUE(source, external_job_id) | de-duplicated by external id and by URL hash |
| **job_matches** | match_id PK, user_id FK, job_id FK, text_similarity, skill_match (nullable), final_score CHECK 0-100, matched_skills, missing_skills (JSON), calculated_at; UNIQUE(user_id, job_id) | cached scores |
| **saved_jobs** | saved_id PK, user_id FK, job_id FK, saved_at; UNIQUE(user_id, job_id) | |
| **applications** | application_id PK, user_id FK, job_id FK, status ENUM(Saved, Applied, Interview, Offer, Rejected, Withdrawn), applied_date, notes, created_at, updated_at; UNIQUE(user_id, job_id) | |
| **career_paths** | career_id PK, career_name UNIQUE, description, interest_area | 15 seeded roles |
| **career_skills** | career_skill_id PK, career_id FK, skill_name, importance 1-3 CHECK; UNIQUE(career_id, skill_name) | 3 = core, 2 = important, 1 = nice to have |
| **career_recommendations** | recommendation_id PK, user_id FK, career_id FK, match_score, skill_alignment, text_similarity, interest_match, matched_skills, missing_skills, reasons (JSON); UNIQUE(user_id, career_id) | recomputed lazily |
| **learning_resources** | resource_id PK, skill_name, resource_name, resource_url, description, resource_type ENUM; UNIQUE(skill_name, resource_url) | 147 seeded links |

All foreign keys use `ON DELETE CASCADE`, so deleting a user or job removes dependent rows.

## Design notes

* Skill lists on jobs and matches are stored as JSON arrays in TEXT columns (per the
  specification's `required_skills` / `matched_skills` / `missing_skills` fields). They are
  derived and cached values, while the normalised data (candidate skills, career skills) lives
  in proper relational tables.
* Indexes cover every lookup path: `(user_id, final_score)` for ranked matches,
  `(user_id, is_active)` for the active resume, `job_url_hash` for de-duplication, and
  `posted_at` / `fetched_at` for newest-first lists.
* No job listings are seeded. Mock jobs exist only if the mock provider is used, and they
  are stored with `source = 'mock'`. Admins can delete them in bulk.

## Regenerating seed data

After changing `backend/app/ml/skill_extraction/taxonomy.py` or `backend/scripts/seed_data.py`:

```bash
cd backend
python scripts/generate_seed.py --admin-email you@example.com --admin-password "S0me-strong-pass"
```

The generator validates that every career skill and resource skill is a canonical taxonomy skill.
